## 3. Batch Safety Gates

### 3.1 Max batch size

| Gate | Value | Rationale |
|---|---|---|
| Max candidates per batch | **10** | Based on single-promotion execution time (~1s per candidate). Larger batches increase rollback cost. |
| Max evidence fields | **10 per candidate** | Matching the existing `EVIDENCE_AXES` constraint. |
| Transaction timeout | **30 seconds** | If not committed within 30s, abort + rollback. |

### 3.2 Failure isolation

```
Per-candidate validation:
  - matched_master_whisky_id NOT NULL (resolved to production whisky)
  - match_status in {exact, normalized_exact, fuzzy}
  - provenance_state NOT in REJECTED_PROVENANCE
  - flavor_vector_json valid (7 canonical axes, each in [0,1])
  - evidence_id not already in flavor_evidence

If any candidate fails pre-validation:
  â†’ Remove from batch; add to `rejected` list
  â†’ Remaining candidates proceed
  â†’ Batch manifest documents accepted/rejected counts
```

### 3.3 Partial success policy

| Outcome | Recovery |
|---|---|
| All candidates pass validation â†’ full promotion | Single transaction, all writes, one commit |
| Some candidates fail validation â†’ partial batch | Successful candidates promoted; failures reported in `rejected` list |
| Transaction failure (IO, integrity, etc.) | **Full rollback**: restore from pre-promotion backup; entire batch retried after investigation |
| Mid-transaction failure of individual INSERT | **Impossible with current model**: all inserts in one transaction â†’ all-or-nothing. Feature gap: per-candidate sub-transactions. |

### 3.4 Rollback scope

| Scenario | Rollback scope | Backup action |
|---|---|---|
| Single candidate fails validation | None (validation only, no DB write) | No backup needed |
| Any candidate fails mid-insert | **Full batch** â€” restore entire `production.db` from pre-promotion backup | Backup required before batch start |
| Post-promotion integrity check fails | **Full batch** â€” restore + investigate | Backup required |
| Post-promotion drift detected (P315 baseline mismatch) | Manual investigation; rollback optional | Backup preserved for comparison |

## 5. Implementation Recommendations

### Phase 1 (immediate, no code change)
- **Manual batch preparation:** Collect N approved staging candidates, generate one batch manifest, execute in a single writer call.
- The existing `EditorialPromotionWriter.execute()` already loops over `prepared` â€” it can handle N candidates if they all pass validation.
- **Blockers:** `matched_master_whisky_id` must be non-NULL for all candidates (writer rejects NULL). This requires a pre-batch matching step.

### Phase 2 (small change)
- **Add matching step** to the orchestrator: match `normalized_name` against `production.whiskies` by normalized name. Store `whisky_id` + `match_status=exact`.
- **Add batch manifest template** as a YAML generator (extend `manifest_PROMO-YYYYMMDD-NNN.yaml`).

### Phase 3 (larger change)
- **Multi-candidate GO form** â€” one form per batch, not per candidate.
- **Partial success policy** â€” sub-transaction per candidate (requires schema review; `flavor_evidence` PRIMARY KEY conflict avoids duplicates).
- **Batch-level audit log** â€” single entry, consolidated metadata.

### Constraints (must NOT change)
- `FIELD_CEILING` in certification engine (frozen Sprint 1 rules)
- `CERTIFY_MIN = 0.70`
- `EVIDENCE_AXES` (7 canonical axes only)
- Deterministic `evidence_id` (SHA-256 based) â€” ensures idempotency
- Read-only production pre-checks (P312/P314/P315 pattern)
